# 複数対戦系列同時進行 システムテストチェックリスト(FEZ-167)

実機のLINEアプリからグループチャットへコマンドを送り、DBとbotの返信メッセージ・画像を目視で確認する。
実施(チェックの消化)は [FEZ-168](https://linear.app/fezzlk/issue/FEZ-168) で行う。対象実装は [FEZ-145](https://linear.app/fezzlk/issue/FEZ-145)(Phase A〜F、PR #258〜#266)。

## 前提

- 検証用のLINEグループを2〜4人で用意する(通常の精算確認のため複数人推奨)。
- 各ケースの実行前に `_matches` や DB を確認し、想定外のopen対戦が残っていないことを確認してから始める。
- 「open対戦」= `status=open` のMatch。精算済みは `status=settled`。

## 複数系列同時進行の核心

- [ ] **新規対戦の明示的な開始**: open対戦が1件もない状態で `_new_match` を送ると、グループの現在の設定(レート等)を反映した確認メッセージが返る
- [ ] `_new_match_confirm` を送ると新しいMatchが作成され、点数入力モードに入る(「第1回戦お疲れ様です」等の開始メッセージ)
- [ ] 既にopen対戦が1件ある状態で `_new_match`→`_new_match_confirm` を実行すると、既存対戦はそのままに2件目のopen対戦が追加される(既存対戦のスコアが変化しない)
- [ ] 入力モード中(`_input`実行後、精算前)に `_new_match` を送ると「すでに入力モードです。」等で拒否される
- [ ] **`_input` のopen件数分岐 — 0件**: open対戦が0件の状態で `_input` を送ると、確認なしで新規対戦が作成され即座に入力が始まる
- [ ] **`_input` のopen件数分岐 — 1件**: open対戦が1件の状態で `_input` を送ると、ピッカーなしでその対戦の入力が始まる
- [ ] **`_input` のopen件数分岐 — 2件以上**: open対戦が2件以上の状態で `_input` を送ると、既存対戦一覧+「新しい対戦を始める」を含むピッカー(Quick Reply)が出る
- [ ] ピッカーから既存対戦を選ぶと、その対戦への入力が始まる(他のopen対戦には触れない)
- [ ] ピッカーから「新しい対戦を始める」を選ぶと、新規対戦が作成されて入力が始まる
- [ ] **`_finish` のopen件数分岐 — 0件**: open対戦が0件の状態で `_finish` を送ると「計算対象の試合が見つかりません。」が返る
- [ ] **`_finish` のopen件数分岐 — 1件**: open対戦が1件なら、ピッカーなしで即座に精算される
- [ ] **`_finish` のopen件数分岐 — 2件以上**: open対戦が2件以上ある状態で `_finish` を送るとピッカーが出て、選んだ対戦だけが精算される(もう一方はopenのまま)
- [ ] **`_active_match` のopen件数分岐 — 0件**: open対戦が0件の状態で `_active_match` を送ると「現在進行中の対戦がありません。」が返る
- [ ] **`_active_match` のopen件数分岐 — 1件**: open対戦が1件なら、ピッカーなしでその対戦の途中経過(半荘結果+グラフ)が即座に表示される
- [ ] **`_active_match` のopen件数分岐 — 2件以上**: open対戦が2件以上ある状態で `_active_match` を送るとピッカーが出て、選んだ対戦の途中経過のみが表示される
- [ ] **並行進行時の独立性**: 対戦Aで点数入力→`_exit`、対戦Bで点数入力→`_exit` を交互に繰り返し、Aの半荘数・スコア・ステータスがBの操作によって変化しないことを `_active_match` や `_matches` で確認する
- [ ] **異なるレートの同時精算**: `_new_match`で対戦Aを作成→`_setting`等でグループのレートを変更→`_new_match`で対戦Bを作成→両対戦にそれぞれ点数を入力して個別に `_finish` し、Aは作成時点のレート、Bは変更後のレートで精算金額が計算されていることを確認する(グループの「現在の」レートに引きずられていないこと)

## 各種ガード

- [ ] 対戦Aが入力セッション中(`_input`実行後、精算/`_exit`前)のときに、`_finish` のピッカーで対戦B(入力セッション外)を選ぶと精算がブロックされ、「現在「(Aの対戦名)」の入力中です。先に完了するか「_exit」で中断してください。」等のメッセージが返る。Bはopenのまま変化しない
- [ ] 上記ブロック後、`_exit` または対戦Aの入力完了で入力セッションを解消してから改めて対戦Bを `_finish` すると、正常に精算できる
- [ ] 統合元グループに進行中(open)の対戦が1件でもある状態で `_migrate_confirm` を実行すると、「統合元・統合先のいずれかに進行中の対戦があるため統合できません。先に精算するか「_exit」で中断してください。」等で拒否され、統合が行われない
- [ ] 統合先グループに進行中(open)の対戦が1件でもある状態で `_migrate_confirm` を実行しても、同様に拒否される
- [ ] 両グループのopen対戦をすべて精算/`_exit`してから `_migrate`→`_migrate_confirm` を実行すると、統合が成功する
- [ ] 個人DM経由の統合(`_personal_migrate`系)でも同じガードが働く(統合元/統合先いずれかにopen対戦があると拒否される)
- [ ] `_reopen` で対戦Aを1件openの状態から再オープンし、別の対戦Bが並行してopen(入力セッション中)であっても、Bの入力セッション(mode/current_input_match_id)が壊れず継続できる
- [ ] 再オープンした対戦Aのレート設定を変更してから再度 `_finish` すると、変更後のレートで再精算される

## 表示

- [ ] このグループが対戦を1件しか持ったことがない(sim除く総数=1)場合、`_finish`結果・`_matches`一覧・`_match N`詳細のいずれにも対戦名が表示されない(従来通りの見た目)
- [ ] 対戦を2件以上持ったことがあるグループでは、`_finish`結果に対戦名が表示される
- [ ] 同条件で `_matches` の一覧表示に各対戦の名前が表示される
- [ ] 同条件で `_match N` の詳細表示に対戦名が表示される
- [ ] `_active_match` の途中経過表示は上記の対戦名表示条件に関わらず、選択した対戦の半荘結果が正しく表示される

## 回帰確認(既存の単一系列フローが壊れていないこと)

- [ ] 対戦を1件も作らず(または前回精算済みの状態から)`_input`→点数入力→`_finish` の一連の流れが、複数対戦対応前と同じ手順・返信で動作する
- [ ] チップ設定(chip_rate≠0)を有効にしたグループで、通常通りチップ入力→精算が動作し、精算金額が正しい
- [ ] 飛び賞(tobi_prize)設定ありの対戦で `_tobi` が正しく反映され、精算結果に反映される
- [ ] 端数計算(rounding_method)の丸めが従来通り機能する
- [ ] `_sim`(シミュレーション)が実系列(open対戦)のデータに影響を与えず、従来通り動作する
- [ ] ゲスト機能(`_setting`からのゲスト追加・削除)が複数対戦の状況でも従来通り動作する
- [ ] `_reopen` が単一対戦のみの状況でも従来通り動作する(直近5件の精算済み対戦から選択できる)
- [ ] `_drop N` で半荘を削除する操作が、複数対戦が同時openな状況でも対象対戦の半荘だけに作用する
